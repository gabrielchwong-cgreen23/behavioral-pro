# BehavioralPro Inference Engine Map

## 1. Vision

BehavioralPro's inference engine exists to turn noisy storefront behavior into usable intervention logic.

At a high level, the engine should:

- collect high-frequency micro-events from Shopify storefront sessions
- preserve those events as a canonical raw behavioral stream
- transform raw events into session-level features
- cluster repeat behavior patterns across many sessions
- infer hesitation states such as trust hesitation, shipping hesitation, or product-fit uncertainty
- improve real-time interventions by feeding validated learnings back into storefront rules

The long-term loop is:

`storefront micro-events -> raw event stream -> session features -> statistical inference -> cluster labeling -> updated intervention rules`

The important design principle is that prediction and interpretation happen after data collection, not instead of it. The system should first observe shopper behavior faithfully, then derive features, then test whether those features actually predict abandonment, conversion, or response to interventions.

## Source of Truth Split

BehavioralPro should explicitly separate three different kinds of truth:

- storefront JS / theme extension = canonical source of client-observed behavioral events
- Shopify server-side events, backend confirmations, and webhooks = canonical source of purchase and revenue outcomes
- Tinybird = canonical analytics event warehouse for unified event storage, aggregation, and feature computation

That distinction matters because client-side JavaScript is the best observer of micro-behavior, but it should not be the only authority for commercial outcomes such as completed purchase and revenue attribution.

## 3. Data Integrity Rules

### Strict Event Naming

All canonical event names should be:

- lowercase
- snake_case
- action-oriented
- semantically stable over time

Avoid mixing synonyms such as:

- `product_view` vs `product_page_view` vs `shopify_product_viewed`
- `begin_checkout` vs `begin_checkout_click` vs `checkout_started`
- `cart_open` vs `cart_viewed`

Recommended rule:

- use one canonical BehavioralPro event name internally
- map external platform names into it at ingestion time

### Session Identity

Every raw event must carry:

- `shop_domain`
- `visitor_id`
- `session_id`

`visitor_id` should persist across sessions when possible.

`session_id` should identify a single browsing session and remain stable across:

- storefront tracking
- backend event ingestion
- Tinybird rows
- Supabase rows
- GA4 mirrored events
- Tidio-triggered interventions

### Deduping

Each event should include a stable `event_id`.

Where user actions are retry-prone or page-refresh-prone, include a deterministic `dedupe_key` in metadata or an equivalent field. The current storefront tracker already does this for several event classes such as:

- purchase
- page view
- product page view
- add-to-cart click
- begin-checkout click

Deduping must happen in at least two places:

- client-side to reduce obvious duplicates
- server-side to enforce idempotency across retries

### Timestamp Consistency

Each event should preserve both:

- `client_timestamp`
- `server_received_at`

The client timestamp reflects shopper behavior timing.

The server timestamp reflects ingestion timing.

Both should be stored in UTC ISO-8601 format. Derived latency and ordering rules should prefer client timestamp where trustworthy, but fall back to server time when missing or clearly invalid.

### Client/Server Event Reconciliation

The client may emit events that the server never receives, and the server may record downstream events not visible to the client.

Examples:

- client emits `begin_checkout`
- server later confirms `purchase`
- server may observe missing session assignment or malformed payloads

Reconciliation rules:

- preserve raw client-side observed events
- preserve authoritative server-confirmed outcomes
- never overwrite raw behavioral observations with derived states
- join client and server records by `shop_domain`, `visitor_id`, `session_id`, and event time windows

### Raw Events vs Derived Features

Raw events are append-only observations.

Derived features are computed summaries of one session or one shopper window.

Examples:

- raw event: `size_chart_open`
- derived feature: `size_chart_count = 3`

- raw event: `coupon_field_focus`
- derived feature: `coupon_focus_count = 2`

- raw event: `purchase`
- derived feature: `converted = true`, `revenue = 129.00`

Do not mix derived features back into the raw event stream except as explicit enrichment tables or downstream model outputs.

## 4. Inference Guardrails

BehavioralPro should keep a strict boundary between observation and interpretation.

- one event does not prove motivation
- hesitation states are provisional labels, not direct truths about shopper intent
- labels require repeated patterns, thresholds, or statistical validation before they should drive strong product decisions
- raw events must remain objective descriptions of what happened, not speculative psychological labels

Examples:

- `return_policy_open` means the shopper opened return policy content
- it does not automatically mean `trust_hesitation`

- `coupon_field_focus` means the shopper focused the coupon field
- it does not automatically mean `price_hesitation`

Interpretation should happen downstream through rules, feature aggregation, clustering, and validation, while the raw event stream stays semantically clean and objective.

## 6. Event Payload Schema

Canonical event payload:

```json
{
  "event_id": "evt_01",
  "shop_domain": "example.myshopify.com",
  "visitor_id": "v_01",
  "session_id": "session_01",
  "client_timestamp": "2026-05-18T12:00:00.000Z",
  "server_received_at": "2026-05-18T12:00:00.350Z",
  "event_name": "product_view",
  "experiment_id": "behavioralpro_revlift_v1",
  "experiment_variant": "behavioral_pro",
  "page_type": "product",
  "page_url": "https://example.com/products/widget",
  "product_id": "shopify_product_123",
  "cart_value": 59.0,
  "cart_quantity": 1,
  "trigger_name": "product_hesitation_rule",
  "message_shown": 1,
  "message_id": "tidio_product_view",
  "intervention_type": "tidio_chat",
  "inferred_state": "product_fit_uncertainty",
  "metadata": {
    "referrer": "https://google.com",
    "traffic_source": "google",
    "device_type": "mobile"
  }
}
```

Field definitions:

- `event_id`: globally unique event identifier
- `shop_domain`: Shopify store domain
- `visitor_id`: persistent anonymous shopper identifier
- `session_id`: session-scoped journey identifier
- `client_timestamp`: timestamp recorded by browser/client logic
- `server_received_at`: timestamp recorded at ingestion time
- `event_name`: canonical event registry name
- `experiment_id`: experiment or rollout identifier
- `experiment_variant`: experiment assignment such as `control` or `behavioral_pro`
- `page_type`: Shopify or derived page type
- `page_url`: current page URL
- `product_id`: current product or line-item product identifier where relevant
- `cart_value`: current cart value snapshot
- `cart_quantity`: current cart quantity snapshot
- `trigger_name`: rule or trigger identifier separate from `event_name` and separate from `inferred_state`
- `message_shown`: numeric or boolean intervention flag such as `0` or `1`
- `message_id`: identifier for the shown intervention when `message_shown = 1`
- `intervention_type`: delivery channel such as `tidio_chat`, `onsite_nudge`, or `none`
- `inferred_state`: optional current rule-based or model-based state label; should remain nullable until inferred
- `metadata`: extensible JSON object for additional event context

Recommended semantics:

- `event_name` = objective observation
- `trigger_name` = why a rule or intervention fired
- `inferred_state` = current best behavioral interpretation

These three fields should not be collapsed into one another.

## 8. Hesitation State Taxonomy

These are first-pass inferred labels, not ground truth labels.

### `trust_hesitation`

- Behavioral evidence: repeated policy review, long dwell without progression, policy loops before exit
- Example micro-events: `return_policy_open`, `policy_loop`, `product_hesitation_12s`
- Possible intervention: reassurance message, returns guarantee, social proof, support prompt
- Statistical validation: label is supported if sessions with these features show materially higher abandonment or delayed checkout and intervention reduces that effect
- Statistical invalidation: label is weakened if these behaviors do not correlate with abandonment or correlate more strongly with another outcome such as healthy comparison browsing

### `shipping_hesitation`

- Behavioral evidence: shipping policy checks, cart review without checkout progression, shipping-related page loops
- Example micro-events: `shipping_policy_open`, `cart_open`, `checkout_back`
- Possible intervention: delivery-time clarity, shipping threshold messaging, shipping FAQ prompt
- Statistical validation: higher abandonment or checkout delay among sessions with shipping-policy behavior; lower abandonment after shipping reassurance intervention
- Statistical invalidation: no measurable link between shipping-policy behavior and downstream abandonment

### `price_hesitation`

- Behavioral evidence: coupon search behavior, quantity edits, cart reopen loops, checkout drop-off after seeing price totals
- Example micro-events: `coupon_field_focus`, `quantity_change`, `cart_open`, `checkout_back`
- Possible intervention: discount framing, bundle messaging, savings explanation, urgency offer
- Statistical validation: these sessions should over-index on abandonment or delayed conversion; price-oriented interventions should improve conversion
- Statistical invalidation: no significant effect on abandonment or no response to price-oriented interventions

### `product_fit_uncertainty`

- Behavioral evidence: size-chart usage, repeated variant changes, long product dwell without cart progression
- Example micro-events: `size_chart_open`, `variant_change`, `product_hesitation_12s`
- Possible intervention: fit guidance, size recommendations, comparison support, concierge chat
- Statistical validation: these features cluster together and predict lower add-to-cart or lower conversion absent intervention
- Statistical invalidation: the same features correspond to normal healthy evaluation among buyers who still convert strongly

### `technical_friction`

- Behavioral evidence: rage clicking, repeated blocked actions, checkout stall without further navigation
- Example micro-events: `rage_click`, `checkout_stall`, repeated `cart_open`/`cart_close`
- Possible intervention: support prompt, alternative checkout path, bug fallback, browser guidance
- Statistical validation: sessions with these features should show sharp drop-offs, unusual latency, or abnormal event sequences
- Statistical invalidation: no association with abandonment or signal disappears after improved instrumentation quality

### `checkout_anxiety`

- Behavioral evidence: begin checkout followed by back navigation, coupon focus, stall before completion
- Example micro-events: `begin_checkout`, `checkout_back`, `checkout_stall`, `coupon_field_focus`
- Possible intervention: trust badges, support prompt, payment clarity, reassurance around checkout safety
- Statistical validation: these features predict abandonment after checkout entry and are separable from generic low intent
- Statistical invalidation: no incremental predictive value beyond ordinary price hesitation

### `high_intent`

- Behavioral evidence: product view to add-to-cart to checkout progression with minimal friction
- Example micro-events: `product_view`, `add_to_cart`, `begin_checkout`
- Possible intervention: light-touch support only, avoid excessive interruption
- Statistical validation: strong conversion rate, short path-to-checkout, positive response to minimal friction design
- Statistical invalidation: cluster splits into multiple subtypes with materially different outcomes

### `low_intent_browsing`

- Behavioral evidence: many page views, shallow product engagement, no cart progress, exit
- Example micro-events: `page_view`, `product_view`, `exit_intent`
- Possible intervention: soft discovery help, recommendations, collection guidance rather than hard conversion prompts
- Statistical validation: weak progression into cart and checkout across many sessions
- Statistical invalidation: users later return and convert at normal rates, suggesting delayed high-intent journeys instead

## 9. Rule-Based Trigger v1

These are first-pass heuristics that can run before full statistical models are mature.

- if `return_policy_open >= 2` within 90 seconds -> infer `trust_hesitation`
- if `shipping_policy_open >= 2` within 90 seconds -> infer `shipping_hesitation`
- if `coupon_field_focus >= 1` and `cart_value > 0` -> infer `price_hesitation`
- if `rage_click_count >= 3` within 5 seconds -> infer `technical_friction`
- if `size_chart_open + variant_change_count >= 3` -> infer `product_fit_uncertainty`
- if `begin_checkout >= 1` and `checkout_back >= 1` -> infer `checkout_anxiety`
- if `product_hesitation_12s >= 1` and `add_to_cart_count = 0` -> infer `product_fit_uncertainty`
- if `page_view_count >= 4` and `cart_open_count = 0` and `begin_checkout_count = 0` -> infer `low_intent_browsing`
- if `product_view >= 1` and `add_to_cart >= 1` and `begin_checkout >= 1` and `rage_click_count = 0` -> infer `high_intent`

These rules should be treated as provisional classification seeds for later validation.

## 11. Jupyter / Statistical Inference Plan

The Jupyter layer should work from exported or queried session-level features, not raw click logs alone.

### Step 1: export or query session features

Pull the `session_features` pipe or an equivalent feature table into Python.

### Step 2: run correlation analysis

Inspect simple relationships such as:

- policy views vs abandonment
- coupon focus vs conversion
- size chart usage vs add-to-cart
- message shown vs downstream purchase by segment

This helps surface which candidate features deserve formal testing.

### Step 3: run chi-square tests

Use chi-square tests for categorical independence questions such as:

- does `shipping_policy_open` correlate with abandonment
- does `message_shown` correlate with conversion
- does inferred `trust_hesitation` differ by `experiment_variant` or intervention type

### Step 4: run logistic regression for abandonment prediction

Fit models where the dependent variable is session abandonment or conversion, using features such as:

- dwell measures
- cart actions
- policy views
- coupon behavior
- frustration signals
- intervention exposure
- experiment variant

The goal is not just predictive accuracy. It is also feature interpretability and directional effect size.

### Step 5: run clustering to discover behavior groups

Use clustering methods such as k-means, hierarchical clustering, or mixture models on normalized session features to identify repeated behavior patterns.

The point is to discover whether the heuristic hesitation taxonomy matches actual behavioral grouping.

### Step 6: compare clusters to inferred hesitation labels

For each discovered cluster:

- inspect dominant features
- compare abandonment and conversion rates
- compare overlap with rule-based hesitation labels
- test whether rules are overfiring, underfiring, or confusing multiple behaviors

## 12. GPT Interpretation Layer

GPT should not make the prediction directly from raw event streams.

Instead, GPT should consume structured outputs such as:

- cluster centroids
- top feature distributions
- regression summaries
- significant chi-square relationships
- intervention response summaries by segment

GPT's role is to:

- label clusters in human language
- explain likely behavioral meaning
- draft merchant-facing narrative summaries
- suggest next hypotheses to test

Example workflow:

`session_features -> clustering/statistics -> structured cluster summary -> GPT labels/explains cluster`

This keeps GPT grounded in measured patterns instead of intuition alone.

## 13. Model Validation Criteria

BehavioralPro should treat validation as part of the product, not an afterthought.

The engine is working only if it satisfies tests like these:

- inferred states should predict abandonment or conversion materially better than a naive baseline
- interventions should improve outcomes inside the relevant inferred state, not just overall averages
- discovered clusters should be stable enough across sessions, time windows, and stores to be useful operationally
- rules should be checked for overfiring and underfiring so they do not label too many low-signal sessions or miss the most important ones

Suggested evaluation views:

- baseline vs inference-model abandonment prediction accuracy
- conversion lift by intervention within each inferred state
- cluster stability across repeated sampling windows
- rule precision and recall against downstream validated outcomes or cluster membership

## 14. Feedback Loop

The feedback loop should work as follows:

1. Storefront tracker records micro-events.
2. Railway validates, timestamps, dedupes, and forwards raw events into Tinybird.
3. Tinybird aggregates raw events into session features.
4. Jupyter/Python tests which features and inferred labels actually correlate with outcomes.
5. GPT interprets cluster summaries and statistical outputs into human-readable insight.
6. Product logic updates:
   - event rules
   - hesitation thresholds
   - intervention targeting
   - intervention copy/channel selection
7. Storefront rules improve over time and are revalidated against new data.

The key idea is that BehavioralPro should evolve from:

- static behavioral heuristics

to:

- measured heuristics backed by statistical validation

and then eventually to:

- adaptive intervention logic informed by both real-time features and validated historical patterns
